1. Executive summary

The AI Interviews frontend is a complete, protected, voice-first mock interview experience. A user creates a session, configures the target role, optionally attaches a stored resume and job description, checks the microphone, records one answer at a time, submits audio, waits for transcription/evaluation, and receives a detailed readiness report.

Frontend status: All screens, route guards, recorder controls, local mock persistence, deterministic questions, a contextual follow-up, answer evaluation, report rendering, retry UX, and history are implemented. The UI depends on an InterviewApi interface, so backend integration belongs in the live adapter rather than page components.
Backend status: No interview endpoints, tables, media storage, transcription jobs, evaluation jobs, or report generation exist yet. The mock implementation uses browser storage and simulated delays only.

Target backend outcome

Build an authoritative asynchronous interview service in the existing FastAPI backend. It must persist sessions across devices, safely accept audio, run transcription/evaluation outside request handlers, guarantee idempotent answer submission, enforce ownership/state transitions, and return stable view models to the frontend.

Recording behavior

  • Microphone access is requested only after a user action.
  • Uses browser MediaRecorder; maximum answer recording is 3 minutes.
  • Device test recording is capped at 10 seconds.
  • The user can pause, resume, stop, replay, and re-record.
  • An empty Blob cannot be submitted.
  • The audio Blob stays in browser memory until upload registration and answer submission succeed.
  • A before-unload warning protects an unsent recording.
  • Media tracks and object URLs are released on replacement/unmount.

5. Audio upload and answer submission

Recommended two-step upload

  1. Frontend records a Blob and keeps it in memory.
  2. POST /interviews/{id}/uploads registers expected media metadata.
  3. Backend returns a short-lived signed object-storage upload URL.
  4. Frontend uploads bytes directly to storage with required headers.
  5. Frontend calls POST /interviews/{id}/answers with the registered media ID and stable idempotency key.
  6. Backend verifies the media object exists, belongs to the user/session, is within limits, and is not already attached elsewhere.
  7. Backend creates one answer transactionally and enqueues processing.
  8. Only after success may the frontend release its recorded Blob.

POST /interviews/{id}/answers

{
  "question_id": "q_uuid",

  "duration_ms": 65000,
  "idempotency_key": "answer_int_uuid_q_uuid_..."
}

202 Accepted
{
  "id": "ans_uuid",
  "question_id": "q_uuid",
  "duration_ms": 65000,
  "status": "queued",
  "created_at": "2026-08-23T12:02:00Z",
  "poll_after_ms": 1000
}
Idempotency requirement: Create a unique database constraint on (user_id, idempotency_key). The same key with the same payload returns the original answer. The same key with a different payload returns 409 idempotency_conflict. This must work across processes and restarts.

Limits and validation

  • Accepted MIME types: browser formats actually supported by product testing (at minimum WebM/Opus; optionally MP4/AAC and Ogg/Opus).
  • Maximum declared/actual recording duration: 180 seconds.
  • Maximum object size: choose a safe value (recommend 25 MB) and enforce in signed upload policy and backend verification.
  • Reject zero-byte objects, mismatched content types, expired registrations, wrong session/user, already-consumed assets, and malware/invalid media.
  • Never proxy large audio through the main API unless object storage is unavailable for the first milestone.

6. Answer processing and next-question logic

Worker pipeline

Verify media
→
Normalize audio
→
Transcribe
→
Evaluate
→
Choose next action
  1. Mark answer queued in the submission transaction.
  2. Worker marks transcribing, downloads/streams the object, and calls the selected transcription provider.
  3. Persist transcript text, provider IDs, language, duration, confidence where available, and sanitized failure details.
  4. Mark evaluating and send question + transcript + role/JD/resume context to the AI service using a versioned structured-output schema.
  5. Validate every score is 0-100 and all arrays/strings meet limits before saving.
  6. Determine next_action: follow_up, next_question, or complete.
  7. Transactionally update answer, current question position, optional follow-up question, and session timestamp.

Follow-up rule

The product allows a maximum of one contextual follow-up per interview. Enforce this server-side with follow_up_used, not only in the prompt. A follow-up should be generated only when it materially probes missing evidence or a useful trade-off; otherwise continue to the next planned question.

Polling now, SSE later

The live adapter should poll the answer endpoint with exponential/backoff-aware intervals (for example 1s, 1.5s, 2s; cap 3s) until completed/failed. Return poll_after_ms. Later, expose an authenticated SSE stream for status events without changing UI domain models.

7. Report generation contract

When the last answer completes, or the user normally completes the interview, transition the session to processing and enqueue a final report job. The report must be reproducible from stored answers/evaluations and include a schema/prompt version.

{
  "overall_score": 79,
  "scores": {
    "relevance": 82,
    "evidence": 73,
    "structure": 78,
    "role_alignment": 80,
    "communication": 84
  },
  "strengths": ["Answers stay relevant", "Clear decision-making"],
  "improvements": ["Add measurable outcomes", "Use a consistent STAR structure"],
  "action_plan": ["Prepare three achievement stories", "Practise 90-second answers"],
  "generated_at": "2026-08-23T12:10:00Z",
  "schema_version": "1.0",
  "evaluation_version": "interview-eval-v1"
}

Aggregation rules

  • Dimension scores should be aggregated consistently across completed answers (document whether equal average or weighted by question type).
  • Overall score must follow the frontend weights in section 3.
  • Report generation should not invent factual evidence not present in transcripts or resume context.
  • Store per-question evaluation separately; the report references it and must survive prompt/model upgrades.
  • If one answer failed permanently, define whether normal completion is blocked or report is generated with a visible incomplete marker.
Current frontend assumption to change in LiveInterviewApi: the mock submitAnswer waits until evaluation completes. The real adapter should accept a 202 queued answer, poll getAnswer, then return the completed view model to the existing page flow.

Required constraints/indexes

  • Foreign keys with deliberate delete behavior; do not cascade away audit-critical answer metadata accidentally.
  • Unique (user_id, idempotency_key) on answers.
  • Unique (session_id, position) on questions.
  • Unique completed answer per (session_id, question_id), or a design that explicitly versions re-attempts.
  • Unique report per session.
  • Indexes on (user_id, updated_at desc), session status, answer status, registered asset expiry, and soft-delete fields.
  • Optimistic version or row lock around current-question advancement to prevent double progression.

9. AI service contracts

The application backend should remain the only service called by the browser. It may call the existing separate AI service using internal authentication/timeouts. Prefer new versioned, structured JSON endpoints rather than reusing text-stream endpoints designed for cover letters.

Suggested internal endpointInputOutput
POST /v1/interviews/questionsRole, type, seniority, duration, sanitized JD, resume snapshotOrdered question plan with stable categories
POST /v1/interviews/evaluate-answerQuestion, transcript, role context, prior answer summary, rubricValidated dimension scores and feedback; optional follow-up intent
POST /v1/interviews/reportSession metadata and completed evaluationsStrengths, priorities, action plan; optionally dimension aggregation explanation

Transcription can be called from the application worker directly or behind the AI service. Whichever owns it must expose provider-neutral results and stable error categories.

Prompt and schema controls

  • Use JSON-schema/structured output and validate before persistence.
  • Version prompts, rubrics, and response schemas.
  • Set deterministic/low-temperature behavior for scoring.
  • Do not score accent, appearance, emotion, protected characteristics, or camera data.
  • Never require video/camera; this product is asynchronous audio only.
  • Apply timeouts, bounded retries, circuit breaking, and provider request IDs.
  • Do not log raw resume/JD/transcript/audio in ordinary application logs.

10. Auth, security, privacy, and product policy

Authentication and authorization

  • Use existing get_current_user; every query must include current user ownership.
  • Return 404, not 403, for another user's interview/media ID to avoid resource enumeration.
  • Resume IDs must be resolved using existing per-user resume semantics.
  • Decide product gating before launch: if paid-only, apply existing require_paid_plan and add an ai_interviews usage feature consistently across config, events, UI, and documentation.

Privacy/retention decisions required

  • Audio retention period (recommend short and explicit, e.g. automatic deletion after 30 days or immediately after transcription if replay history is not needed).
  • Transcript/report retention and account-deletion behavior.
  • User-visible consent language and privacy-policy update.
  • Encryption in transit and at rest; private buckets only.
  • Signed URL expiration and object key randomization; never expose permanent public URLs.
  • Deletion job must remove storage object and mark/delete DB records according to policy.
  • Redact secrets/PII from tracing and provider logs where possible.

Abuse/cost controls

  • Rate-limit session creation, upload registration, answer submission, polling, and retries.
  • Cap concurrent active sessions and queued jobs per user.
  • Count billable work when a transcription/evaluation job is accepted, not for harmless GET polling.
  • Validate declared size/duration against actual media metadata.
  • Set global worker concurrency and provider budget alarms.

HTTPCode examplesFrontend behavior
400/422validation_error, unsupported_media, empty_recordingShow field/recording guidance
401authentication_requiredExisting refresh/login flow
402requires_planExisting upgrade modal, if gated
404interview_not_found, answer_not_foundRecover to history with message
409state_conflict, idempotency_conflict, question_already_answeredRefetch authoritative session
410upload_expiredRegister a new upload; retain blob
413/415media_too_large, unsupported_mediaExplain recording requirements
429usage_limit_reached, too_many_requestsRespect Retry-After / existing modal where applicable
500/502/503processing_failed, provider_unavailableKeep recording if submission not accepted; otherwise poll/retry job

Retry semantics

  • Upload URL expired before upload: register a new media asset.
  • Upload succeeded, answer POST timed out: resend the exact same idempotency key/payload.
  • Transcription/evaluation failed after answer accepted: do not re-upload; retry the server job.
  • Client refresh during processing: GET /interviews/{id} must recover state.
  • Worker crash: queued/in-progress jobs must be reclaimable using leases/timeouts.

13. Required tests and acceptance criteria

Backend automated tests

  • Setup validation, resume ownership, enum/duration/JD limits.
  • Every allowed and forbidden session transition.
  • Concurrent start and concurrent answer submission.
  • Same idempotency key/same payload returns same answer.
  • Same idempotency key/different payload returns 409.
  • Wrong user cannot read/delete/upload/submit against another session.
  • Signed upload expiry, size/MIME mismatch, missing object, consumed media.
  • Worker retry and stalled-job recovery.
  • Maximum one contextual follow-up.
  • Score validation and weighted overall calculation.
  • Normal completion, early abandonment, final report, delete/media cleanup.
  • Refresh/poll recovery at queued/transcribing/evaluating/processing states.

Definition of done

  • A user can create an interview using a resume they own.
  • Refresh at any route returns the user to the authoritative stage.
  • An uploaded answer cannot be lost or double-billed after a network timeout.
  • Audio is private, bounded, and deleted according to documented policy.
  • Answer status is observable until completed or safely retryable.
  • The next question/follow-up cannot advance twice under concurrency.
  • The final report matches the required dimensions and weights.
  • Frontend can switch to VITE_INTERVIEW_API_MODE=live without rewriting screens.
  • Logs/metrics make provider failures and stuck jobs diagnosable.
